从 GPT-4 到 DeepSeek-R1：我做 LLM 代码评审的 18 个月

发表于2025-06-15|更新于2025-06-15|AI算法
|总字数:4.1k|阅读时长:13分钟|浏览量:

2024 年 1 月，我把 GPT-4 接进了代码评审；2025 年 2 月，我让 DeepSeek-R1、GPT-4o 和 4o-mini 在同一套多智能体系统里分工。这篇不讲全部细节，只记下几条现在看来依然成立的判断，以及它们分别形成于什么时候。

毕业季，正好把这一年半做的事情盘一遍。

这件事从 2024 年初的一个小工具开始，后来成了我硕士毕业设计的主线：让大模型评审一整个代码项目，而不只是一段代码。

18 个月里，我用过的底座模型换了四代：GPT-4（8K）→ GPT-4 Turbo（128K）→ GPT-4o / 4o-mini → DeepSeek-R1。每换一次，都有一些当初以为是”模型不够强”的问题，被证明其实是”架构没想清楚”。

00｜先把时间钉住

时间 我做了什么 当时的背景
2024-01 第一版跑通：上传代码文件，GPT-4 按 6 个维度评审打分，随后 Docker 部署 GPT-4 Turbo（128K）还处于 preview
2024 Q1 切到 gpt-4-0125-preview，单次处理上限从 8K 升到 128K；支持上传整个项目 zip 做项目级评估，3 月底已在线上运行 gpt-4-0125-preview 于 1 月 25 日发布
2024-05 研究方向定为”目标驱动的 LLM 多智能体 × 静态代码分析” 多智能体的公开工作大多在”写代码”
2024-05 ～ 07 项目包规模做到 500+ 文件，加入 token 预算与文件筛选；底座切到 GPT-4o GPT-4o 于 5 月 13 日发布
2024-09 写下”多 Agent 的价值来自差异，而不是数量”的笔记 MCP、A2A 都还没有发布
2024-12 算清”Token 爆炸”，画出”逐文件评审 + 结构化笔记 + 汇总”的新架构 Magentic-One 刚发布一个月
2025-01-20 — DeepSeek-R1 发布
2025-02 中旬 完成 3 个模型、7 种组合、5 个真实项目的对照实验 R1 发布后的第 3～4 周
2025-02 下旬 毕业论文定稿 —

表里的每个时间点，都能用当时的版本日志、文件时间戳和论文定稿交叉核对。之所以先列时间，是因为这个领域变化太快：同一个判断，早半年说是洞见，晚半年说就是常识。

01｜2024.01：先让 LLM 当评审，别急着让它改代码

第一版的功能很朴素：上传一个代码文件，GPT-4 从注释、命名、格式、冗余、安全、性能 6 个维度打分，指出问题，给出修改建议。

当时我刻意定了一条边界：只评审，不直接返回”修好的代码”。

理由很简单。模型对代码的理解还远没到”几乎不出错”的程度，让它直接改写，引入新 bug 的风险无法忽略；而评审意见需要经过人来采纳，模型的错误会被人过滤一层。同样的模型能力，放在”建议”的位置上，比放在”执行”的位置上安全得多——评审是容错率最高的切入点。

另一个很早就有的体感是：能力门槛是真实存在的。我给模型写的是一套分层提示词——角色定义、评审逻辑、输出模板分开组织。GPT-3.5 读不懂这么长的组合指令，换到 GPT-4 才稳定下来。所以之后每次换模型，我先问的都是”它能不能稳定执行这套结构”，而不是先看榜单分数。

02｜2024.03–07：窗口变大，问题不会自己消失

2024 年初，我把模型换成 gpt-4-0125-preview，单次能处理的长度从 8K 一下跳到 128K。直觉上，似乎终于可以把整个项目一股脑塞进去了。

于是有了项目级评估：上传整个项目的 zip，给出综合结论。3 月底它已经在线上跑；到年中，单个项目包能处理 500 多个文件，底座也换成了刚发布的 GPT-4o。

现实很快泼了冷水。第一版项目级评估的做法，是把文件一个接一个放进同一个对话，指望模型靠上下文”记住”前面看过的代码。它很快撞上两堵墙：单次请求超出窗口，以及按分钟计的 token 限流。

我当时的权宜之计，是一个按文件体积筛选的”Top-K”：从大到小累加 token，到预算为止，剩下的小文件不评。它在一个真实项目上翻了车——项目里混进了一个后缀罕见的大日志文件，预算被它一个吃光，最后只剩 1 个文件进入评审。

这件事给我的教训至今有效：

在 LLM 系统里，最先出问题的往往不是模型，而是喂给模型的东西。 文件白名单、编码识别、空文件和超大文件的剔除，这些不起眼的”脏活”决定了系统的下限；而”按体积挑重要文件”这种看似合理的启发式，在真实项目里可能完全失效——体积和重要性之间没有必然联系。

03｜2024.09：多 Agent 的价值来自”差异”，不是”数量”

2024 年 5 月，我把研究方向定为”目标驱动的 LLM 多智能体 × 静态代码分析”。那时公开的多智能体工作大多集中在”写代码”上（ChatDev、MetaGPT 这一类），”评代码”方向屈指可数，CodeAgent 是少数之一。

定方向容易，难的是回答一个更根本的问题：底层都是同一类 LLM，为什么需要多个 Agent，而不是一个更强的模型？

2024 年 9 月，我在笔记里写下了自己的回答，大意是：

  • 多个 Agent 的价值，来自它们之间的差异：不同的上下文、不同的数据、不同的工具、不同的模型。可以定义一个”技能重合度”——两个 Agent 能力的交集占并集的比例越低，分工能覆盖的范围就越大；
  • 但差异有一个前提：它们之间必须有一块共同的”语言”，否则就是鸡同鸭讲，信息流传不过去；
  • 反过来，如果几个 Agent 用同一个模型、看同样的上下文、拿同样的工具，那所谓”多智能体”只是把一次调用拆成了几次，徒增 token。

现在回看，这条判断经住了时间。后来出现的 MCP（2024 年 11 月）和 A2A（2025 年 4 月），在工程上处理的都是”共同语言”这一层；而今年 3 月一篇系统分析多智能体失败原因的论文也发现，很多多智能体系统相对单 Agent 基线的提升并不明显，失败大量出在规格设计和 Agent 之间的协作环节——多 Agent 不等于更好，差异和接口才是收益的来源。

04｜2024.12：Token 爆炸是平方级的，记忆不该是聊天记录

到 2024 年底，我把”一个长对话”的问题彻底算清楚了。

flowchart LR
    F1[文件 1] --> CH((同一个对话<br/>每轮重发全部历史))
    F2[文件 2] --> CH
    FN[文件 n] --> CH
    CH --> R1[项目报告]

在这种模式下，第 k 次请求要把前 k−1 个文件和它们的评审结果全部重发一遍。设每个文件 t 个 token、每份评审 r 个 token，n 个文件的累计输入大约是：

累计输入 ≈ n² ×（t + r）÷ 2

是平方级，不是线性。 用一组示意参数算一下（系统提示 2K、每个文件 3K、每份评审 0.8K token；仅为示意，不是实测）：

项目文件数 一个长对话（累计输入） 逐文件评审 + 笔记（累计输入） 相差
10 约 22 万 约 6 万 3.7 倍
20 约 82 万 约 12 万 7.0 倍
40 约 316 万 约 23 万 13.5 倍
80 约 1241 万 约 47 万 26.6 倍

而且按这组参数，到第 34 个文件时，单次请求就已经超过 128K 窗口。窗口再大，平方级的增长迟早会追上它。

2024 年 12 月，我画出了新架构，核心只有一句话：不再把聊天记录当记忆。

flowchart LR
    G1[文件 1] --> J1[评审 Agent]
    G2[文件 2] --> J2[评审 Agent]
    GN[文件 n] --> JN[评审 Agent]
    J1 --> NB[(结构化笔记)]
    J2 --> NB
    JN --> NB
    NB --> SA[汇总 Agent] --> R2[项目报告]
  • 评审 Agent 每次只看一个文件，彼此独立、互不依赖；
  • 每看完一个文件，把结论写成一条结构化笔记（文件、发现的问题、各维度结果、耗时），存进共享的笔记本；
  • 汇总 Agent 只读笔记，不读源码，产出项目级报告。

累计成本从平方级降到线性；而且因为每次评审互相独立，天然可以并行。

设计记忆时，我对比过两种主流做法：一种是 LangChain 式的”保留对话历史 / 最近 N 轮”，另一种是 Magentic-One 式的”把任务状态存成变量、注入提示词”。前者简单，但长任务必然溢出；后者轻快，但多个 Agent 的中间状态很难回溯。我选了第三条路：每个 Agent 写自己的结构化笔记，持久化、可回放、可审计。

把这一节压成一句话：

上下文不是聊天记录，而是需要被设计的工作内存——放什么、以什么结构放、谁来读，都应该是显式的设计决策。

05｜2025.02：按”调用次数”和”输入长度”给角色配模型

2025 年 1 月 20 日，DeepSeek-R1 发布。第 3 到 4 周，我把它接进系统，和 GPT-4o、4o-mini 组成 7 种”汇总 + 评审”组合，在 5 个真实项目上做对照，每种组合重复采样 3 次。

下面几条结论，到今天仍是我给 Agent 选模型的基本思路。

1. 评审位被调用 n 次，汇总位只被调用 1 次。 系统的耗时和成本主要由评审位的模型决定。只要组合里有 R1，耗时就明显上升；而按调用次数推算，让慢思考模型坐在高频的评审位，代价远大于让它坐在汇总位。

2. 初审不需要最强的模型。 在所有组合都跑得通的项目上，双 4o-mini 组合的通过情况与 4o + 4o 一致，成本最低。逐文件初审是”广度”任务，便宜、快、稳定，比聪明更重要。

3. 汇总位是”低频 + 长输入”。 推理模型理论上很适合放在低频的汇总位，可汇总位恰恰是整条链路里输入最长的地方。我当时接入的 R1 接口单次能接收的长度偏短，以 R1 做汇总的组合在大项目上没能跑完，手动缩短输入后才恢复正常。所以汇总位需要的是”推理能力 + 长上下文”，或者干脆把汇总本身也分层。

4. 不变的放前面，变化的放后面。 评审位每次调用的角色提示词完全相同，变化的只有文件内容。把固定部分放在最前面，就能吃到服务商的上下文缓存：在一次对照里，R1 命中缓存后耗时下降了 47.9%。成本上，一个 65 行的文件用 R1 生成一份完整的评审报告，花费约 0.066 元。

给 Agent 选模型：先看它被调用多少次，再看它的输入有多长，最后才看它需要多聪明。

06｜LLM 会”编数字”：评测比系统更难

一开始，我用”各维度打分”作为主要指标。分数的波动太大，后来改用”各维度检测到的问题数”，以为数个数总比打分客观。

直到把实验数据画成热力图，我才看出问题：

在规模最大的那个项目上，60 个”问题数”里有 49 个是 5 的倍数，约 82%；而在中等规模的项目上，这个比例只有约 24%，接近整数随机分布下大约五分之一的预期。

10、15、20、25……这些数字不是数出来的，是”估”出来的。当输入超出模型能逐条核对的范围，它就会用整数凑一个看上去合理的总数。

这件事把我之前的几条直觉连成了原则：

  • 凡是后续要拿去计算的数字，都不该让模型”写”出来，而应该让程序”算”出来。 让模型逐条列出问题（文件、位置、类型），由代码去计数；
  • “发现的问题更多”不等于”更准”。 没有标准答案时，多出来的可能只是幻觉；
  • 失败的运行要记成缺失值，不能画成 0——0 会被读成”没发现问题”。

另一个体会是：评测集比系统更难做。公开的代码数据集，要么是单函数级别的 bug，要么是海量代码的统计，都对不上”项目级、多语言、真实工程”这个场景。我最后自己挑了 5 个真实项目，从一百来行的单文件，到三万多行、混着前后端和视觉模型的系统。真实项目很”脏”——奇怪的后缀、混乱的编码、被提交进仓库的日志——但恰恰是这些脏东西，才测得出系统的下限。

07｜一个没来得及做完的设计：会说”我还没想清楚”的反思者

在最初的”目标驱动”方案里，我还设计过一个反思者 Agent。它不直接干活，只负责观察，在关键时刻纠错或给出提示。它的提示词围绕三个问题展开：

  • 是什么：当前发生了什么，现状如何；
  • 为什么：现状背后的原因，按优先级排列；没想清楚之前，不进入下一步；
  • 怎么办：只有前两个问题想清楚了，才给出建议。

其中我最看重的一条规则是：如果没想清楚，或者不确定建议能否解决问题，就保持沉默，提示需要更多信息。

让 Agent 学会”弃权”，比让它更能说重要得多。这个设计没赶上毕业，我把它留给下一个版本。

08｜我准备怎样推翻自己

一个结论，只有说清楚”什么结果会推翻它”，才算一个结论。接下来我最想检验三件事：

  1. 收益到底来自”多智能体”，还是来自”记忆设计”？ 做消融：单 Agent 配同样的结构化笔记，对比多 Agent。如果单 Agent 也能拿到同样的成本和效果，那”多智能体”在这个任务里就只是一个名字。
  2. 便宜模型做初审，到底够不够？ 往项目里注入已知缺陷，用 precision / recall 衡量，并和传统的规则型静态分析工具同场比较。
  3. 跨文件的问题会不会丢？ 逐文件评审天然看不到”A 文件里定义、B 文件里误用”这类问题。分层汇总能否在保持成本线性的同时把它们找回来，才是这套架构真正的考验。

写在最后

这 18 个月里，模型从 8K 窗口走到 128K，从”快思考”走到”慢思考”，同等能力的价格降了不止一个数量级。

但回头看，真正决定系统上限的，始终是三件与具体模型无关的事：

喂什么（输入筛选），记什么（记忆结构），谁来算数（数字由程序而不是模型给出）。

模型会继续换代，这三件事不会过时。

同一件事，为什么不同管理者会问出完全不同的问题？ 一次会议上，我听到一位高阶管理者向另一位资深同事询问一件事：是否涉及监管上报？ 这个问题很短，却让我产生了一个很长的念头。 我最初下意识地把它翻译成技术人的语言：他是不是只想知道“有没有出事”？如果没到监管上报的程度，难道问题就不严重、不值得继续讨论了吗？ 但回过头仔细想，我可能理解错了。 01｜同样是在问影响面，问的却不是同一个问题技术人员谈事件，往往先关心爆炸半径：哪些系统受影响？涉及多少用户？持续了多久？有没有数据泄露、资产损失或服务中断？根因能否确认？ 这是在还原事实，并评估事件本身的技术影响。 我又联想到过去观察过的另一类资深管理者。他们往往也会沿着这条路径追问影响范围和根因。但这只是我对不同场景的横向观察，并不意味着那位管理者参与了当天的会议。 而“是否涉及监管上报”实际上可能是在问另一件事：事件是否已经触发法律或合规领域的响应义务？是否需要让法务、隐私、公共事务或其他责任团队介入？组织是否要面对新的时限、沟通口径和外部责任？ 技术团队是在判断“事情影响了什么”；另一种管理视角则在判断“这件事需要谁共同负责”。...
